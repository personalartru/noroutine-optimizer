# Оптимизатор — пошаговый MAX-бот

Отдельный бот [@se14730534_1_bot](https://max.ru/se14730534_1_bot): шесть
коротких вопросов — на выходе часы рутины, их стоимость, экономия, чек-лист
внедрения, примерный бюджет и заявка владельцу. Раньше жил кнопкой внутри
лид-бота канала (`personalartru/noroutine_growth`), теперь это отдельный
проект и отдельный бот; кнопку из старого бота вырезаем после приёмки этого.

## Как устроено

Два файла, граница между ними принципиальна.

`optimizer.py` — чистая стейт-машина: семь сфер, роли с типовыми зарплатами,
рутинные операции, инструменты, расчёт экономии, все тексты и клавиатуры. Не
знает про MAX API, импортирует только `html`, `os`, `re`, `time`. Возвращает
список сообщений `{"text": …, "buttons": [[…]]}`; сообщение с ключом `admin`
транспорт пересылает владельцу. Благодаря этому весь флоу прогоняется локально
без токена.

`max_bot.py` — транспорт: long polling `GET /updates`, доставка в личку,
ответы на `callback`, соответствие `user_id → chat_id` диалога, хранение шага
диалога и offset, пересылка заявки. Токен читается из окружения, при его
отсутствии `main()` возвращает 2 и честно пишет почему.

Шаги: сфера → кого оптимизируем (один или команда, мультивыбор специальностей
+ количество кнопками 1–5, диапазоном или числом сообщением) → рутинные
операции → часы и стоимость → инструменты (плюш шуточный «Уволить всех») →
экономия и чек-лист → бюджет, дисклеймер и кнопка «💬 Отправить заявку».
Сессия живёт 40 минут (`SESSION_TTL`), дальше обычные сообщения снова просто
сообщения.

## Ограничения MAX, о которые спотыкались

Бот пишет только тем, кто его запустил, — поэтому если личка недоступна, на
клик отвечаем `POST /answers`, а не молчим. `chat_id` диалога не равен
`user_id`: писать нужно на `chat_id` из события, иначе `404 chat.not.found`.
Текст режется по 900 символов (`TEXT_CHUNK`). У каждой кнопки обязан быть
`type` — без него MAX молча не показывает клавиатуру (на этом и умер финальный
шаг в проде). payload держим коротким id.

## Секреты

| Секрет | Значение |
|---|---|
| `MAX_BOT_TOKEN` | токен бота @se14730534_1_bot |
| `MAX_ADMIN_CHAT_ID` | ваш user_id в MAX, куда приходят заявки — `60669315` (в workflow уже стоит значением по умолчанию) |
| `DISPATCH_TOKEN` | classic PAT со scope `repo` + `workflow` — нужен, чтобы цикл ставил следующий сам |
| `LEAD_BOT_TOKEN`, `LEAD_ADMIN_CHAT_ID` | необязательно: Telegram-уведомления сторожа |

Вы должны один раз нажать «Начать» в этом боте от своего аккаунта: иначе
заявка с финального шага не доставится — бот пишет только запустившим его.

## Где работает

Цикл ~9 минут long polling в GitHub Actions, workflow
`run-optimizer.yml`, самопереочередь через `repository_dispatch`. Push в main
по `max_bot.py` / `optimizer.py` тоже запускает цикл — деплой отдельного не
нужно. Версия кода в логе: «MAX-бот «Оптимизатор» запущен (версия <short-sha>)».

Состояние (`.max_offset`, `.max_dialogs.json`, `.max_optimizer.json`) живёт в
`actions/cache` с ключом `optimizer-state-*`; новый state-файл нужно добавить в
оба шага кэша.

**Логика очереди.** Циклы сериализуются `concurrency.group: optimizer-v1` с
`cancel-in-progress: false` — идущий опрос не прерывается. Но такая группа
хранит в очереди ровно одного: новое поступление вытесняет предыдущий queued.
Поэтому шаг переочереди сначала смотрит, свободен ли слот, и не встаёт, если
там уже стоит прогон push (он и так возьмёт свежий main). Если слот свободен,
dispatch повторяется до трёх попыток с проверкой результата; не вышло — шаг
падает с `::error::`, чтобы мёртвая цепочка была видна в списке прогонов.
Страховка — `lead-bot-watchdog.yml` (cron `*/15` плюс ручной запуск): если ни
один цикл не опрашивает и в очереди нет актуального прогона, сторож ставит
новый и проверяет, что dispatch сработал; зависший queued-прогон вытесняется.
Планировщик GitHub при нагрузке пропускает cron, так что сторож — страховка, а
не двигатель.

Важно: в workflow без шага `checkout` `gh` не выводит репозиторий из
git-контекста — везде передаём `--repo personalartru/noroutine-optimizer` явно.

## Проверки перед push

```bash
python3 tools/simulate_optimizer.py --quiet    # 5 сценариев + инварианты клавиатур, optimizer-preview.html
python3 tools/check_max_bot.py                 # 30 интеграционных проверок с заглушкой MAX API
python3 tools/fuzz_optimizer.py --runs 800     # случайные payload'ы и тексты + обход всех сфер
```

Симулятор не трогает транспорт, поэтому главный регресс на изменение
`optimizer.py` — именно он. `check_max_bot.py` ставит заглушку на
`max_bot.call` и проверяет обвязку: маршрутизацию callbacks, хранение шага,
доставку заявки, поведение без лички и просроченной сессии.

## Ссылка на финальном шаге

После заявки бот предлагает два действия: «🔧 Оптимизатор заново» (callback) и
«Канал про автоматизацию» — ссылка `https://max.ru/channel_noroutine`. URL
берётся из переменной репозитория `MAX_CHANNEL_URL` (в workflow есть дефолт,
так что переменную заводить не обязательно), поэтому сменить канал можно без
пуша кода.

Обратно — в этом репозитории: кнопка «Оптимизатор» в старом лид-боте
(`personalartru/noroutine_growth`) пока жива и вырезается отдельным шагом;
до того как новый бот приняли, правки стейт-машины приходится ношить в оба
репозитория.
